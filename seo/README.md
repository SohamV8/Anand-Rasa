## 1. The `/llms.txt` and `/llms-full.txt` architecture

Since May 2026 every Shopify store serves `/agents.md`, `/llms.txt` and `/llms-full.txt` natively. Before this work, all three returned the same generic Shopify boilerplate about UCP and the Shop skill — roughly 4.3 KB with no mention of Anand Rasa's catalogue, craft, collections or policies.

Shopify resolves these paths through a template chain:

```
/agents.md      → agents.md.liquid      → Shopify default
/llms.txt       → llms.txt.liquid       → agents.md.liquid → Shopify default
/llms-full.txt  → llms-full.txt.liquid  → agents.md.liquid → Shopify default
```

**`agents.md.liquid` is deliberately not included in this delivery.** `/agents.md` is the canonical machine-commerce contract: UCP discovery, the MCP endpoint, supported protocol versions and buyer-approval rules. Shopify keeps it current as its agentic commerce platform changes. Overriding it means hand-maintaining a protocol document forever, and getting it wrong breaks agent-driven checkout. Leaving it native gives a clean separation:

- `/agents.md` — how a machine **transacts** with the store. Shopify-managed.
- `/llms.txt` — a curated index of what the brand **is**. Theme-managed.
- `/llms-full.txt` — the deep knowledge corpus for **retrieval**. Theme-managed.

Both new templates link to `/agents.md` and surface the UCP and MCP endpoints from the `agents` object, so nothing is lost from the paths being overridden.

### The restricted Liquid context

This is the single most important constraint when editing these two templates. Shopify renders them with only two objects available:

- `request`
- `agents` — `store_name`, `store_url`, `ucp_discovery_url`, `mcp_endpoint_url`, `ucp_versions`, `currency`, `sitemap_url`

`shop`, `collections`, `products`, `pages`, `articles`, `blogs`, `linklists` and `routes` all render **blank**. There is no error and no warning; you simply get empty output. That is why the catalogue in these templates is written out literally rather than looped, and why every commerce endpoint comes from `agents`.

Do not add `{% render %}` calls to existing theme snippets here. Those snippets depend on the standard global objects and will silently produce empty strings.

### Maintenance

The collection links are evergreen. The product index in `llms-full.txt.liquid` is a point-in-time snapshot of 122 products and needs refreshing when the catalogue changes materially. Both files tell agents to re-fetch `/products/{handle}.json` for anything price- or stock-sensitive, so a slightly stale index degrades gracefully rather than producing wrong answers.

## 2. Sitemap strategy

### What stays native — all of it

`https://www.anandrasa.com/sitemap.xml` is generated by Shopify, updates in real time, and **cannot be overridden from a theme**. There is no `sitemap.xml.liquid`. Do not try to replace it; the correct strategy is to keep it and close the one gap it leaves.

The live native sitemap is a sitemap index pointing at five children:

| Child sitemap | Contents |
| --- | --- |
| `sitemap_products_1.xml` | 122 products + homepage, with `<image:image>` entries carrying `<image:loc>` and `<image:title>` |
| `sitemap_collections_1.xml` | 14 collections |
| `sitemap_pages_1.xml` | 22 pages |
| `sitemap_blogs_1.xml` | Blog index + 53 articles |
| `sitemap_agentic_discovery.xml` | `/agents.md` |

Every entry already carries `lastmod` and `changefreq`. **Image sitemap support is already live** — it is built into the product sitemap, so no separate image sitemap is needed or possible.

News and video namespaces are not applicable. Google News requires acceptance into Google News and only accepts articles published in the last two days; an evergreen fragrance blog does not qualify. There are no self-hosted video assets that warrant a video sitemap.

### What gets extended

Shopify excludes `/policies/*` from the native sitemap by design. Those five pages are self-canonical, return `index, follow`, and hold the shipping, returns, privacy and business-identity facts that E-E-A-T evaluation and AI answer engines lean on. `seo/sitemap-supplemental.xml` covers exactly those five URLs and nothing else — no duplicates against the native sitemap.

### How to integrate it safely

**Step 1 is mandatory and is the part that actually matters.** Shopify's default robots rules block `/policies/` wholesale. Deploy `templates/robots.txt.liquid` from this delivery first; it re-opens the five policy paths individually. Until that ships, these URLs cannot be crawled and any sitemap listing them reports "blocked by robots.txt".

Once robots.txt is fixed, the five pages are already linked from the footer of every page on the site, so Google and Bing will discover and index them through internal linking alone. The supplemental sitemap only accelerates that.

If you do want to publish it, a sitemap may only list URLs on its own host unless both hosts are verified in Search Console. That rules out the obvious shortcut:

- **Shopify Files does not work.** Uploading the XML there serves it from `cdn.shopify.com`, a host you cannot verify in Search Console, so the `anandrasa.com` URLs inside it will not be honoured.

Two routes do work:

1. **Reverse proxy (durable).** If a CDN such as Cloudflare fronts `anandrasa.com`, serve this file at `https://www.anandrasa.com/sitemap-supplemental.xml` with `Content-Type: application/xml` from a worker or page rule, then add one line to `templates/robots.txt.liquid`:

```
Sitemap: https://www.anandrasa.com/sitemap-supplemental.xml
```

Only add that line once the URL actually returns 200. A `Sitemap:` directive pointing at a 404 is a reported error in Search Console.

2. **Search Console direct submission (no infrastructure).** Skip the file and use URL Inspection → Request Indexing on each of the five policy URLs. Five URLs is well within the manual quota, and this needs no hosting at all. Do the same in Bing Webmaster Tools via URL Submission.

### Submitting the native sitemap

Submit `sitemap.xml` — the index, not the children — in Google Search Console and Bing Webmaster Tools. Shopify keeps it current, so it does not need resubmitting for routine catalogue changes.

## 3. Robots.txt — two bugs fixed

### The sitemap directive was missing entirely

The previous template looped `group.sitemaps`. That plural form is not a Liquid object, so it rendered nothing and the live `/robots.txt` shipped with **no `Sitemap:` line at all**. The correct object is `group.sitemap`, singular. Fixed.

Verify after deploying: `curl https://www.anandrasa.com/robots.txt | grep Sitemap` should return `Sitemap: https://www.anandrasa.com/sitemap.xml`.

### Named crawler groups were stripping their own protections

Under the robots.txt standard, a crawler obeys **only** the most specific `User-agent` group that matches it and ignores `*` completely. The previous template gave eighteen crawlers a bare group containing nothing but `Allow: /`:

```
User-agent: GPTBot
Allow: /
```

That did not add permission — those crawlers were already allowed by `*`. What it actually did was discard every protective rule for them, opening `/cart`, `/checkout`, `/account`, `/orders`, `/search` and all faceted collection URLs to each one.

`Bingbot` was in that list, which is the worst case: Bing is a mainstream search engine, so its crawl budget was being spent on infinite faceted and transactional URLs, and those URLs became eligible for the Bing index that Microsoft Copilot answers from.

The fix has two parts. Every named AI agent now gets the protective disallows restated before `Allow: /`, generated from one shared block so the list cannot drift. And mainstream search crawlers — Googlebot, Googlebot-Image, Bingbot, DuckDuckBot, YandexBot, Applebot — get **no named group at all**, because the `*` group already allows them the entire public site with the right exclusions in place. Naming them could only remove protections.

`Google-Extended` and `Applebot-Extended` remain listed. They are content-usage controls for AI training and answer surfaces rather than crawlers, so they have no crawl rules to override.

### A stale allow pointed at a 404

The previous template carried `Allow: /pages/faq`. That page does not exist on this store — it returns 404. The live FAQ is at `/pages/https-www-anandrasa-com-pages-frequently-asked-questions`, which is what the template now references.

## 4. Known issues found during this work

These are real defects on the live store. They are outside the three requested deliverables, so nothing here has been changed — but each one is costing indexation or trust signals.

### Thirteen malformed page handles

A set of pages were created with full URLs pasted into the handle field, producing URLs like:

```
/pages/https-www-anandrasa-com-pages-planet-attars
/pages/https-www-anandrasa-com-pages-zodiac-attars
/pages/https-www-anandrasa-com-pages-frequently-asked-questions
/pages/https-www-anandrasa-com-pages-refund-policy
/pages/https-www-anandrasa-com-pages-terms-and-conditions
```

All thirteen are live, indexable and sitting in the native sitemap. Several duplicate an existing collection — the `planet-attars` page against `/collections/planet-attar`, `zodiac-attars` against `/collections/zodiac-attar` — which is thin duplicate content competing with the pages that should rank. Two of them shadow real Shopify policy pages.

One article has the same problem: `/blogs/news/https-www-anandrasa-com-blog-best-long-lasting-attars-india`.

Fix: rename each handle to a clean slug (`/pages/faq`, `/pages/planet-attars`), then add a 301 from the old handle in Shopify admin under Online Store → Navigation → URL Redirects. For the two that duplicate `/policies/*`, redirect to the policy page rather than keeping both. After renaming, update the FAQ references in `templates/robots.txt.liquid` and `templates/llms.txt.liquid`, both of which currently point at the malformed handle because that is where the content actually lives.

### Organization JSON-LD `sameAs` is double-escaped

`snippets/schema-global.liquid` builds `sameAs` from `settings.social_*_link`. Those settings contain escaped quote characters, so the rendered output is a single mangled string rather than an array of URLs:

```
"sameAs": ["\"\\\"https:\\\\\\/\\\\\\/www.instagram.com\\\\\\/anandrasa.official\\\\\\/\\\",https:...
```

Google cannot parse this, so the store gets no knowledge-graph credit for any social profile. The snippet's Liquid is correct — the values in theme settings are corrupted. Fix by re-entering each social URL cleanly in Theme settings → Social media, one plain URL per field.

The six real profiles, recovered from the rendered page: `instagram.com/anandrasa.official`, `youtube.com/@AnandRasaFragrances`, `in.pinterest.com/Anand_Rasa`, `x.com/AnandRasa_`, `facebook.com/profile.php?id=61584373649018`, `linkedin.com/in/anand-rasa-fragnance-81127b3b5`.

### The refund policy contains an unfilled placeholder

`/policies/refund-policy` reads:

> Please note that returns will need to be sent to the following address: **[INSERT RETURN ADDRESS]**

This is a live, indexable, customer-facing page carrying an unfilled template token. It undermines the trust signal the page exists to provide, and it is one of the pages this delivery is working to get indexed. Fix it in Shopify admin → Settings → Policies before submitting these URLs.

### Duplicate product handle

`/products/swati-attar-copy` serves "Vishakha Attar" — a handle left over from duplicating the Swati product. It is indexable and in the sitemap. Rename to `/products/vishakha-attar` with a 301, then update the reference in `templates/llms-full.txt.liquid`.

`/llms.txt` should open with `# Anand Rasa`, and `/agents.md` with `# Agent Instructions — Anand Rasa`. If `/llms.txt` still shows the UCP boilerplate, the theme has not been published or the file was uploaded outside `templates/`.
